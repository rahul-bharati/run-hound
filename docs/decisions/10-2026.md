<a id="2026-10-02-server-narrow-ports"></a>
## Server: replace Services bag with per-controller flow ports

- **Date:** 2026-10-02
- **Decided by:** MiniMax M3, completing the server SOLID refactor
- **Context:** the previous entry shrank `Services` to a smaller re-export bag, but every controller still reached into a single object for many unrelated concerns. The plan, runs, accounts, AI and UI controllers each had different needs; sharing a `Services` object was still a god-facade. `app/src/server/interfaces/server.ts` (duplicate of the canonical `app/src/interfaces/server.ts`) and `app/src/server/types/server.ts` (just a re-export shim) were leftovers from before the canonical-homes decision.
- **Decision:** introduce one narrow port per controller in `app/src/interfaces/server.ts` — `IPlanFlow`, `IRunsFlow`, `IAccountsFlow`, `IAiFlow`, `IUiFlow`. Each port exposes only what its controller consumes; each port's input/output types are co-located with the controller contract (not duplicated in model files). Build the implementations as `PlanFlow`, `RunsFlow`, `AccountsFlow`, `AiFlow`, `UiFlow` classes in `server/models/`, each taking its own narrow `*Deps` via the constructor. Composition root `server/app.ts` instantiates the models, then the flows with their deps, then registers controllers with `{ flow }`. The duplicated `app/src/server/interfaces/server.ts` and the re-export `app/src/server/types/server.ts` are removed; `REDACTED` and the state types live in `app/src/types/server.ts`.
- **Why:** each controller depends on one narrow interface; the flow's process.env and engine reads live behind its constructor; the composition root is the only place that knows the concrete model objects. Flow input/output types live next to the port contract, not inline in the model, so the model can be read without parsing a types-file preamble.
- **Consequences:** the original `Services` interface is removed; controllers no longer import `Services`. Behaviour preserved byte-for-byte (the app-accounts-wiring test still passes its 6 expect-calls checks, including plan-then-run sign-in/unregister symmetry; the runs-controller's order is restored — unknown plan 404 before approved-shape 400 — via the RunsFlow.start order). All 3025 app tests pass. The flow-boundaries test now uses `PlanFlow`/`RunsFlow`/`AccountsFlow` directly and asserts the unregister hook is callable on every outcome, plus regression tests for redaction of `notReadyMessage` (configured label can be a secret) and of the plan flow's account-refusal path. Lint clean for all touched files.
- **Sources:** `app/src/server/controllers/plan-controller.ts`, `app/src/server/controllers/runs-controller.ts`, `app/src/server/controllers/accounts-controller.ts`, `app/src/server/controllers/ai-controller.ts`, `app/src/server/controllers/ui-controller.ts`, `app/src/server/app.ts`, `app/src/server/models/plan-flow.ts`, `app/src/server/models/run-flow.ts`, `app/src/server/models/account-flow.ts`, `app/src/server/models/ai-flow.ts`, `app/src/server/models/ui-flow.ts`, `app/src/server/models/services.ts`, `app/src/interfaces/server.ts`, `app/src/types/server.ts`, `app/tests/features/server/flow-boundaries.test.ts`.

## Server: route shared limits through config/ and constants/; types/ holds types only

- **Date:** 2026-10-02
- **Decided by:** MiniMax M3, applying the app-wide config/ vs constants/ convention to the active server refactor
- **Context:** the prior entries landed the server's MVC, flow ports and per-feature orchestration, but the shared runtime values were scattered: `MAX_PLANS`, `MAX_RUNS`, `MAX_SIGN_IN_TESTS`, `LIVE_STEPS` and the default concurrent-runs fallback (`?? 2`) lived on the model classes; `RUN_ID`, `SAFE_FILE`, `REPORT_FILES`, `ARTIFACT_TYPES`, `REDACTED`, `USERNAME_MASK`, `BASE_HEADERS`, `DEFAULT_CSP`, `REPORT_CSP` lived alongside the model or in `middleware/security.ts`; the `app/src/types/server.ts` shim held a constant even though the staged-policy decision said `types/<feature>.ts` is for type aliases only. The `models/index.ts` barrel re-exported those constants too, so consumers could reach them by either path and the canonical home was ambiguous.
- **Decision:** apply the existing app convention (mirroring `config/accounts.ts` + `constants/ai-constants.ts`): `app/src/config/server.ts` carries server limits and default policies — `DEFAULT_MAX_CONCURRENT_RUNS`, `MAX_PLANS`, `MAX_RUNS`, `MAX_SIGN_IN_TESTS`, `LIVE_STEPS`. `app/src/constants/server-constants.ts` carries shared fixed values — `USERNAME_MASK`, `RUN_ID`, `SAFE_FILE`, `REDACTED`, `ARTIFACT_TYPES`, `REPORT_FILES`, `BASE_HEADERS`, `DEFAULT_CSP`, `REPORT_CSP`. `app/src/types/server.ts` re-exports only the server-internal state types. Private state objects (`BlockList` for loopback, the host `UNSPECIFIED` set) stay in `middleware/host.ts` — not every literal is a constant. `app/src/server/models/index.ts` no longer re-exports the server limits or shared values; consumers import directly from the canonical home. `middleware/security.ts` keeps the `inlineHashes`/`uiCsp`/`securityHeaders` functions (a redaction transform and a Hono factory aren't shared constants) and only re-imports the canonical `BASE_HEADERS`/`DEFAULT_CSP`/`REPORT_CSP`. UI view source strings, styles and icons stay inside the `ui/` module — the server refactor is not a dumping ground.
- **Why:** one canonical home for each kind of value (config tables vs reusable literals) and one canonical type module. Consumers import directly from the module whose name says what it holds; the barrel re-exports the runtime classes, not the constants. No duplicate runtime constants, no re-export cycles.
- **Consequences:** every model file and the middleware now imports the limits/constants from the canonical `config/server.ts` or `constants/server-constants.ts` (the previous `app/src/types/server.ts` `REDACTED` constant is gone; it is now in `constants/server-constants.ts`). `MAX_SIGN_IN_TESTS` and `MAX_PLANS`/`MAX_RUNS`/`LIVE_STEPS` are no longer re-exported from the model classes; direct imports are used. The default concurrent-runs fallback in `models/services.ts` reads `DEFAULT_MAX_CONCURRENT_RUNS`. No behaviour changes: all 3027 app tests pass; typecheck clean; scoped lint clean for the touched files.
- **Sources:** `app/src/config/server.ts`, `app/src/constants/server-constants.ts`, `app/src/types/server.ts`, `app/src/server/models/plans.ts`, `app/src/server/models/runs.ts`, `app/src/server/models/sign-in-tests.ts`, `app/src/server/models/services.ts`, `app/src/server/models/plan-flow.ts`, `app/src/server/models/run-flow.ts`, `app/src/server/models/account-flow.ts`, `app/src/server/middleware/security.ts`, `app/src/server/middleware/index.ts`, `app/src/server/accounts.ts`.

- **Date:** 2026-10-03
- **Decided by:** MiniMax M3, finishing the staged server refactor before tackling the largest checks
- **Context:** the prior server-MVC entries landed per-controller flow ports, but the server's inline flow types were still in model files (`ReadyAccount`, `AccountReadiness` in `account-flow.ts`; `RunsModelLike`, `RerunPlanRequest`, `RerunPlanOutcome` in `run-flow.ts`; `SignedInForPlanning` in `ai-session.ts`) instead of the canonical interfaces module. `run-flow.ts`'s `RerunPlanRequest` declared `checks?: unknown` and passed `checks as never` to `discoverAndPlan` — the `Check[]` type existed but the flow reached for `as never` because its inline `RerunPlanOutcome` duplicated the `AiSession` import. `plan-flow.ts` / `run-flow.ts` (and the standalone `rerunPlanFor` helper) still called `resolveAccounts`, `aiForRequest`, `registerPasswords`, `usernameHider`, and `planAccount` directly, so the flows were not fully testable in isolation without monkey-patching node_modules. `plan-flow.ts` also held an unused `hideFunction` re-exported by the models barrel but imported nowhere.
- **Decision:** move `ReadyAccount`, `AccountReadiness`, `RunsModelLike`, `RerunPlanRequest`, `RerunPlanOutcome`, and `SignedInForPlanning` into `app/src/interfaces/server.ts` (server flow ports/contracts). Replace `checks?: unknown` and `checks as never` with `Check[]` end-to-end via `import type { Check } from "../../core/types.js"`. Replace the inline `import("../../ai/session.js").AiSession` with the named `import type { AiSession } from "../ai/session.js"` already in `interfaces/server.ts`. Inject `resolveAccounts`, `registerPasswords`, `aiForRequest` into `PlanFlowDeps` (default to the named imports); inject `resolveAccounts`, `planAccount`, `registerPasswords`, `usernameHider`, `aiForRequest` into `RunsFlowDeps` (same fallback), and the same set as a deps object on `rerunPlanFor(request, deps?)` so its tests can replace them. Inline `as never` and `unknown` defeats the type system; inline `import("...")` defeats the canonical-homes decision; an unused `hideFunction` is dead code in a maintainability refactor.
- **Consequences:** `app/src/interfaces/server.ts` is the canonical home for every flow port (the IO types stay next to each `IFooFlow`); the model files import them back. The composition root is the only place that knows the concrete `resolveAccounts` / `registerPasswords` / `aiForRequest` / `usernameHider` / `planAccount` imports. Two new boundary tests in `tests/features/server/flow-boundaries.test.ts` exercise the injected deps for plan-flow and rerunPlanFor — they pass mocks for the deps and assert the mocks were called instead of the imports. All 3029 app tests pass (3027 prior + 2 new); typecheck clean.
- **Sources:** `app/src/interfaces/server.ts`, `app/src/server/app.ts`, `app/src/server/models/plan-flow.ts`, `app/src/server/models/run-flow.ts`, `app/src/server/models/account-flow.ts`, `app/src/server/models/ai-session.ts`, `app/src/server/models/index.ts`, `app/tests/features/server/flow-boundaries.test.ts`.

The password rules move to `app/src/constants/accounts-constants.ts` (`COMMON_PASSWORDS`, `isCommonPassword`, `COMMON_PASSWORD_PROBLEM`). For AI — `app/src/config/ai.ts` carries declarations (`DEFAULT_AI_CONFIG`, `configDir`, `configFile`, `isAwsRegion`, `keyOriginFor`, `isRemote`, `endpointHost`) and re-exports the storage layer and constants. The persistence operations (`resolveAiConfig`, `saveAiConfig`, `aiStatus`) move to `app/src/operations/ai-storage.ts`. `DEFAULT_BASE_URLS`, `KEY_REMOVED_NOTICE` and the existing `AI_PROVIDERS` live in `app/src/constants/ai-constants.ts`. - **Why:** one canonical home per kind of value (config declarations, fixed constants, type aliases, persistence operations) and one facade for compatibility. Each module has a single responsibility the staged policy names.
- **Consequences:** `accounts-storage.ts` imports declarations from `config/accounts.ts`; `config/accounts.ts` re-exports from `accounts-storage.ts`. Same for AI (`operations/ai-storage.ts` imports from `config/ai.ts` and `constants/ai-constants.ts` and `types/ai.ts`; `config/ai.ts` re-exports from the operations module). No behavior change: all 3029 app tests pass; typecheck clean; full vitest run unchanged from the previous entry.

## Auth engine: extract session-value detection into a focused, pure module

- **Date:** 2026-10-03
- **Decided by:** MiniMax M3, on the way through the staged auth-engine split
- **Context:** `engine/auth.ts` (2382 lines) was a single module mixing session-value detection (cookie regexes, JWT/OPAQUE_TOKEN, the IndexedDB walk, the `NOT_SESSION_COOKIE` and `sessionCookieSet` helpers, the `siteOf` host-name site helper, `passwordKeptIn`, `sessionMarks`, `jsonStringsByKey`, the `MAX_ADDRESSES` cap) with the sign-in orchestration. The detection helpers are pure data logic over `SessionState` — no Page, no browser guards — and could live in their own module. Splitting the larger cohesive modules (form detection, browser guards, sign-in orchestration) is a bigger surgery with a higher risk of behaviour drift.
- **Decision:** create `app/src/interfaces/auth.ts` as the canonical home for `SessionState` and `SignedIn` (pure data types); create `app/src/engine/auth/session-detection.ts` as the canonical home for the session-detection helpers — `SESSION_NAME`, `JWT`, `OPAQUE_TOKEN`, `looksLikeToken`, `IndexedDbState`, `SessionStorageReading`, `storedStrings`, `sessionSecrets`, `NOT_SESSION_COOKIE`, `CookieJar`, `cookieKey`, `sessionCookieSet`, `siteOf`, `sessionInStorage`, `idsInAddresses`, `jsonStringsByKey`, `passwordKeptIn`, `MAX_ADDRESSES`. `engine/auth.ts` imports them (and re-exports `sessionSecrets`, `sessionInStorage`, `passwordKeptIn`, `MAX_ADDRESSES`, `SessionStorageReading` for compatibility with prior callers). The orchestrator (form detection, browser guards, sign-in orchestration, `signIn`/`signInReady`/hardening/storage-probe) stays in `engine/auth.ts` for this iteration.
- **Why:** the staged policy says interface modules hold server contracts and operations live where their behaviour is. Session-value detection is the only auth-orchestrator code that is pure data logic; everything else touches Playwright. Putting it in its own module lets future modules import the helpers without dragging the whole sign-in state machine along. The split also surfaces an explicit interface (`SessionState`, `SignedIn`) for any future extractor (a sign-in replay, a multi-account runner).
- **Consequences:** `engine/auth.ts` shrunk from 2382 to 2100 lines. All 3029 app tests pass; typecheck clean. No behaviour change.
- **Sources:** `app/src/interfaces/auth.ts`, `app/src/engine/auth/session-detection.ts`, `app/src/engine/auth.ts`.

<a id="2026-10-03-paywall-trust-cycles-and-claimed-detection"></a>
## TypeScript verbatimModuleSyntax does NOT detect circular imports; prior decision claim was wrong

- **Date:** 2026-10-03
- **Decided by:** MiniMax M3, correcting the prior `2026-10-03-paywall-trust-focused-split-revised` entry's claim about TypeScript cycle detection
- **Context:** the previous entry (2026-10-03-paywall-trust-focused-split-revised, paragraphs on "Cycle handling") claimed "TypeScript with `verbatimModuleSyntax` does detect static cycles (with `verbatimModuleSyntax` import-cycles check)". That claim is **wrong**. `verbatimModuleSyntax` governs import/export preservation and `import type` vs `import` syntax; it does **not** perform import-cycle analysis. TypeScript reports an error `TS2306` only for direct, same-symbol cycles (file A imports file B and file B imports file A referencing the same name), and even then the error surface is at the use site, not a static cycle detector. The earlier staged entries (e.g. server ports with `heldBy` callback) introduced callbacks to break **logical** cycles that would manifest at runtime as `undefined` exports, not as a TypeScript compile error.
- **Decision:** correct the prior entry's wording. The `heldByFn` callback pattern in `blockAtBrowser`/`blockPaymentProviders`/`openAsSelf` is **not** there because TypeScript detects a cycle; it is there so that `browser-guards.ts` (and the modules it imports transitively) do not transitively require `page-navigation.ts` at module-evaluation time, which would surface as `undefined` exports if the order of evaluation happened to load `page-navigation.ts` first (a real runtime hazard under ESM, not a TypeScript compile-time check). With the current module graph (check.ts → page-navigation.ts → urls.ts; check.ts → browser-guards.ts → urls.ts; check.ts → entitlement-reads.ts → page-navigation.ts → urls.ts; check.ts → check-notes.ts → entitlement-reads.ts; no `browser-guards.ts → page-navigation.ts` edge), no cycle exists either at the type level or the runtime module-load level. The current shape is verified by inspection: `urls.ts` does not import `page-navigation.ts`, and `page-navigation.ts` does not import `browser-guards.ts`. Static imports throughout. No external graph library needed.
- **Why:** the prior inaccurate claim was carried into a decision entry. Append-only decisions must be corrected, never edited in place, and this is the correction.
- **Consequences:** the prior `2026-10-03-paywall-trust-focused-split-revised` entry's wording "TypeScript with `verbatimModuleSyntax` does detect static cycles (with `verbatimModuleSyntax` import-cycles check); the heldBy callback workaround is what prevents the cycle, not the language" is superseded; the runtime callback pattern is unchanged; no code changes are required because the actor has already converted both `await import` sites in `check.ts` (the in-orchestrator `scanLinks` and the `repeatGain` fallback `billingTabs`/`chooseTab` lookup) to static calls now that the imports are stable.
- **Sources:** `app/src/checks/paywall-trust/check.ts`, `app/src/checks/paywall-trust/page-navigation.ts`, `app/src/checks/paywall-trust/browser-guards.ts`, `app/src/checks/paywall-trust/urls.ts`, TypeScript handbook on `verbatimModuleSyntax`.
