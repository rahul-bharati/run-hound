<a id="2026-09-21-docker-local-no-hosted-platform"></a>
## Run Hound ships as a Docker image that runs on the user's own machine, with no hosted platform for now

- **Date:** 2026-09-21
- **Recorded:** 2026-09-26, from commits `76fb653` and `c2daf62` (README.md, "Delivery")
- **Decided by:** Rahul Bharati (maintainer)
- **Context:** The first README, written before any code, set out how Run Hound would reach its users.
- **Decision:** Delivery is Docker-based: users pull the image and run it locally, and the local web UI for approving the plan is served from the container. There is no hosted platform for now (the first draft, `76fb653`, said "no online platform (temporary)"). The initial scope is testing localhost; live sites, mostly staging and dev, come later.
- **Why:** not recorded.
- **Consequences:** Vibe coders are "the least likely to run Docker and a local LLM, so they are served later through hosted inference or a hosted runner" (README.md "Who it's for", `16630dd`), which the business model keeps as a possible paid tier ([2026-09-21](#2026-09-21-checks-never-paywalled)). The images are published on GHCR ([2026-09-25](#2026-09-25-images-on-ghcr)), and since 0.4.1 one `docker pull` and one `docker run` start Run Hound ([2026-09-26](#2026-09-26-pull-and-run-first)).
- **Sources:** commits `76fb653` (README.md, "Delivery") and `c2daf62` (README.md, "Delivery" and "Tech stack"); the section now lives in [docs/overview.md](../overview.md#delivery).

<a id="2026-09-21-only-owned-targets"></a>
## Run Hound tests only targets the user owns: localhost and private addresses by default, other domains after ownership verification

- **Date:** 2026-09-21
- **Recorded:** 2026-09-26, from commit `c2daf62` (README.md, "Security")
- **Decided by:** Rahul Bharati (maintainer)
- **Context:** The first README (`76fb653`, "Security Issues") named misuse, scanning websites or apps the user doesn't own, as the security problem to solve.
- **Decision:** localhost and private IPs are allowed by default. Any other domain requires ownership verification before it can be scanned: either a DNS TXT record or a nonce placed in a `<meta>` tag in the HTML header, and the scan only runs where the nonce is found. "Only owned targets, safe by default" became one of the design principles the same day (`16630dd`).
- **Why:** "Users must not be able to misuse Run Hound to scan websites/apps they don't own." (README.md, "Security", at `c2daf62`; now [docs/security.md](../security.md#security))
- **Consequences:** V0's safety gate enforces the default, and a test account's sign-in page must pass the same gate ([docs/v0-spec.md](../v0-spec.md#engine), "Engine"; [docs/v2-spec.md](../v2-spec.md#test-accounts), "Test accounts"). Ownership verification is not built yet: other hosts get through only when listed in `RUNHOUND_ALLOWED_HOSTS`, which is not checked ([2026-09-22](#2026-09-22-allowed-hosts-unchecked)). Testing live staging and dev sites behind ownership verification is V4, and the business model lists "domain verification for live sites is planned (V4)" ([docs/business-model.md](../business-model.md#open-core-vs-paid), "Open core vs paid").
- **Sources:** commits `76fb653` (README.md, "Security Issues"), `c2daf62` (README.md, "Security") and `16630dd` (README.md, "Design principles"); the section now lives in [docs/security.md](../security.md#security).

<a id="2026-09-21-destructive-actions-opt-in"></a>
## Destructive actions stay off unless the user explicitly opts in

- **Date:** 2026-09-21
- **Recorded:** 2026-09-26, from commit `c2daf62` (README.md, "Security")
- **Decided by:** Rahul Bharati (maintainer)
- **Context:** Run Hound drives the app under test in a real browser and runs the scenarios the user approves (README.md, "Our solution to this", `c2daf62`).
- **Decision:** "No destructive actions (real payments, deleting data) unless the user explicitly opts in." V0 made it concrete: "Destructive scenarios are off unless `--allow-destructive`; so are controls whose name says they destroy, pay for or send something" ([docs/v0-spec.md](../v0-spec.md#engine), "Engine", from `b934920`).
- **Why:** not recorded.
- **Consequences:** 0.2.0 counts "Log out", "Sign out", "Cancel subscription", "Close account", "Empty cart" and similar as destructive, so they are never clicked by default. In 0.3.0 the AI plan review never ticks a destructive scenario, and suggested flows can't activate destructive controls without `--allow-destructive`. While signed in (0.4.0), Run Hound never clicks sign-out controls and never submits a form that sets a password, even with `--allow-destructive`. Checks that write never call sign-out, password, email, account-deletion, payment-provider, invitation or sharing endpoints, even with `--allow-destructive` ([2026-09-26](#2026-09-26-write-side-safety-contract)).
- **Sources:** commits `c2daf62` (README.md, "Security") and `b934920` ([docs/v0-spec.md](../v0-spec.md#engine), "Engine"); [CHANGELOG.md](../../CHANGELOG.md) "0.2.0", "0.3.0" and "0.4.0"; [docs/signed-in-runs.md](../signed-in-runs.md).

<a id="2026-09-21-deterministic-checks-decide"></a>
## Pass or fail comes from deterministic checks with evidence, never from a model

- **Date:** 2026-09-21
- **Recorded:** 2026-09-26, from commit `16630dd` (README.md, "Design principles")
- **Decided by:** Rahul Bharati (maintainer)
- **Context:** The first plan had the AI take screenshots, read them with vision and generate the scenarios to verify (`76fb653`, "Our solution to this").
- **Decision:** Two design principles. "The LLM plans and explains; deterministic checks decide. Pass/fail comes from Playwright assertions, axe-core rules and captured traffic, never from model judgement. Findings that depend on judgement (e.g. alt-text quality) are marked advisory." And "No evidence, no finding. Every reported defect has a screenshot and/or request/response, plus a replayable spec."
- **Why:** "Made-up defects are the biggest product risk, especially for non-technical users." (README.md, "Design principles", at `16630dd`; now [docs/overview.md](../overview.md#design-principles))
- **Consequences:** From 0.1.0, findings are confirmed or advisory: `run` exits 0 with no confirmed findings (advisory ones don't fail the run), 1 with at least one confirmed finding, and 2 on an error or a refused target; every finding has evidence and an exported Playwright spec. The fixtures measure made-up findings through a clean mode ([2026-09-21](#2026-09-21-planted-bug-fixtures)). The principle has read "AI plans and explains; real checks decide" since the site went AI-forward (`10ebec6`), and "The model never decides pass or fail" is the first rule of the AI layer ([2026-09-25](#2026-09-25-ai-optional-off-by-default)).
- **Sources:** commit `16630dd` (README.md, "Design principles"; now [docs/overview.md](../overview.md#design-principles)); [CHANGELOG.md](../../CHANGELOG.md) "0.1.0 (V0 tester preview)"; commit `10ebec6`.

<a id="2026-09-21-checks-never-paywalled"></a>
## Every check stays in the open core; a possible paid tier, only after demand is validated, would cover things that run on our servers

- **Date:** 2026-09-21
- **Recorded:** 2026-09-26, from commit `16630dd` ([docs/business-model.md](../business-model.md#principles), "Principles")
- **Decided by:** Rahul Bharati (maintainer)
- **Context:** The business model was written before any code, as a proposal: "Nothing here is built yet. Monetization comes after the open-source core has real users."
- **Decision:** The open core includes every check (functional, accessibility, security), the approval UI, reports, Playwright export, bring-your-own-model support and the test fixtures. "Never paywall a check." A possible paid tier, later and only after demand is validated, would cover things that run on our servers: hosted inference, a hosted runner, team dashboards, CI integration and compliance exports. It would be unlocked with an API key passed to the Docker container; without a key, the core runs fully.
- **Why:** "Finding the holes is the mission and the source of trust, and free alternatives exist (Playwright's test agents, axe, platform scanners; see research.md). A weakened free tier loses to them." The paid column is mostly server-side: "it runs on our infrastructure, so it has value that can't be patched out of an open-source image."
- **Consequences:** Nothing paid is built, and Run Hound does not read `RUNHOUND_KEY` today ("API key in the Docker command"). The order is to ship the free core and get real users, measure demand, then build the paid piece with the clearest demand first, most likely hosted inference ("Validate before building billing"). The core's license was chosen at the public launch ([2026-09-25](#2026-09-25-mit-license)).
- **Sources:** commit `16630dd` ([docs/business-model.md](../business-model.md), "Principles", "Open core vs paid", "Validate before building billing"; README.md, "License and business model").

<a id="2026-09-21-planted-bug-fixtures"></a>
## Run Hound is developed and scored against deliberately broken test apps with planted bugs and a clean mode

- **Date:** 2026-09-21
- **Recorded:** 2026-09-26, from commit `16630dd` ([docs/fixtures.md](../fixtures.md#why-fixtures), then titled "Why a fixture")
- **Decided by:** Rahul Bharati (maintainer)
- **Context:** Run Hound needs ground truth: "we know exactly which bugs are planted, so we can measure what Run Hound finds, what it misses, and what it makes up" (docs/fixtures.md at `16630dd`).
- **Decision:** Run Hound is developed and scored against Kennel, a deliberately broken app. Every planted bug sits behind its own toggle, and `none` is the clean mode, where every finding counts as a false positive. Scoring covers planted bugs found, false positives in clean mode, stability across repeated runs, and evidence on every finding.
- **Why:** "Safe and legal. Everything is owned and local, so two-account checks and writes can run freely." "Measurable. Planted bugs give recall; the clean mode gives false positives." Made-up findings are the biggest product risk, "so this is the primary quality metric". "Reproducible": the same state on every run and in CI.
- **Consequences:** V0's done criterion was that Run Hound finds the V0 bugs planted in Kennel and reports nothing in its clean mode (README.md, "V0: Single form", `16630dd`). The acceptance suite, added in `b934920` against Kennel, now runs Run Hound against both fixtures and the sample apps in CI on every pull request and every push to main ([docs/fixtures.md](../fixtures.md#scoring), "Scoring"). Well-built sample apps joined in 0.1.0 as a false-positive suite, and Fernway in 0.4.0 ([2026-09-26](#2026-09-26-fernway-over-supabase-kennel)). Repeating runs to check that findings are stable is still planned.
- **Sources:** commit `16630dd` (docs/fixtures.md, "Why a fixture" and "Scoring"; README.md, "Test fixture" and "V0: Single form"); commit `b934920`; [docs/fixtures.md](../fixtures.md), "Why fixtures" and "Scoring".

<a id="2026-09-22-pnpm-hoisted-linker"></a>
## The pnpm workspace uses the hoisted node linker

- **Date:** 2026-09-22
- **Recorded:** 2026-09-26, from commit `b934920` ([pnpm-workspace.yaml](../../pnpm-workspace.yaml))
- **Decided by:** Rahul Bharati (maintainer)
- **Context:** The commit that added the V0 engine, Kennel and the acceptance suite introduced the pnpm workspace (`app`, `fixtures/kennel`, `tests/acceptance`).
- **Decision:** `nodeLinker: hoisted` in `pnpm-workspace.yaml`.
- **Why:** "pnpm 12.3.4 fails to materialise peer-less variants of vitest for the kennel package; the hoisted linker sidesteps it and keeps resolution simple for this small workspace." (the comment in `pnpm-workspace.yaml`)
- **Consequences:** The Docker image's start needed a fix for it: "Docker image starts (tsx path under the hoisted linker)" (`fed1819`). The Run Hound image installs with pnpm's isolated linker instead, so only Run Hound's own production dependencies land in it: "the hoisted layout would also bring Kennel's and Fernway's React packages" ([app/Dockerfile](../../app/Dockerfile), the install step's comment).
- **Sources:** commit `b934920`; [pnpm-workspace.yaml](../../pnpm-workspace.yaml); commit `fed1819`; [app/Dockerfile](../../app/Dockerfile).

<a id="2026-09-22-allowed-hosts-unchecked"></a>
## Until ownership verification exists, hosts listed in RUNHOUND_ALLOWED_HOSTS pass the safety gate without an ownership check

- **Date:** 2026-09-22
- **Recorded:** 2026-09-26, from commits `b934920` ([docs/v0-spec.md](../v0-spec.md#engine), "Engine") and `727d8a5` (README.md, "Security")
- **Decided by:** Rahul Bharati (maintainer)
- **Context:** Ownership verification ([2026-09-21](#2026-09-21-only-owned-targets)) was not built for V0.
- **Decision:** The safety gate accepts a target whose host is `localhost` (or `*.localhost`), an IP literal in a private range, a name that resolves only to private addresses, or a name listed in `RUNHOUND_ALLOWED_HOSTS`; anything else is refused before a browser opens. The list is not checked for ownership: "Other hosts are refused unless listed in `RUNHOUND_ALLOWED_HOSTS`, which is not checked for ownership, so list only hosts you own." (README.md, "Security", from `727d8a5`)
- **Why:** not recorded.
- **Consequences:** A name approved through DNS is pinned, and a navigation guard stops navigations to hosts the gate refuses ([docs/v0-spec.md](../v0-spec.md#engine)). `client-only-validation` runs on localhost targets only, "even when the host is in `RUNHOUND_ALLOWED_HOSTS`" (docs/v0-spec.md, "Checks and accepted responses"). Since 0.4.1 the image lists `host.docker.internal` and `host.containers.internal`, which only ever point at the machine running the container ([2026-09-26](#2026-09-26-pull-and-run-first)).
- **Sources:** commit `b934920` ([docs/v0-spec.md](../v0-spec.md#engine), "Engine", item 1 "Safety gate"); commit `727d8a5` (README.md, "Security"); [docs/security.md](../security.md#safety).

<a id="2026-09-25-ai-optional-off-by-default"></a>
## AI is optional, off by default and bring-your-own-model, and a model never decides pass or fail

- **Date:** 2026-09-25
- **Recorded:** 2026-09-26, from commit `3a3caab` ([docs/ai-spec.md](../ai-spec.md#rules), "Rules")
- **Decided by:** Rahul Bharati (maintainer)
- **Context:** 0.1.0 and 0.2.0 used no model. From 2026-09-24 the site, then the README and TESTING.md, led with AI planning, explanations and bring-your-own-model, labelled "Coming soon" (`10ebec6`, `1b0287f`). The contract for 0.3.0's AI layer came next.
- **Decision:** The AI rules: "The model never decides pass or fail." It recommends and ranks built-in scenarios, composes flows from a fixed step vocabulary whose assertions are deterministic, and writes advisory text. "Off by default": `enabled: false` until the user turns it on. A local endpoint needs no consent; a remote one, and Bedrock always, is refused until the user consents. Only redacted page structure is sent. AI failure never blocks. The user brings the model: Ollama, any OpenAI-compatible endpoint, or Amazon Bedrock, with no new dependencies.
- **Why:** not recorded in docs/ai-spec.md; the pass-or-fail rule restates [the 2026-09-21 principle](#2026-09-21-deterministic-checks-decide).
- **Consequences:** With AI off, 0.3.0's plans, runs and reports were byte-for-byte what 0.2.0 produced, apart from the version. Findings from AI-suggested flows are advisory. The acceptance suite doesn't expect AI-only checks to plan or pass without a model (`7fd7c7c`). Since 0.4.0 the AI review can tick a scenario but never untick one that is ticked by default. Shipped in 0.3.0 ([PR #3](https://github.com/rahul-bharati/run-hound/pull/3)).
- **Sources:** commits `3a3caab` ([docs/ai-spec.md](../ai-spec.md#rules), "Rules") and `8d72ec3`; [PR #3](https://github.com/rahul-bharati/run-hound/pull/3); [CHANGELOG.md](../../CHANGELOG.md) "0.3.0" and "0.4.0"; [docs/ai.md](../ai.md).

<a id="2026-09-25-contracts-and-failing-tests-first"></a>
## Each slice starts with a contract and failing tests, and the implementation comes after

- **Date:** 2026-09-25
- **Recorded:** 2026-09-26, from commits `3a3caab` and `50bb559`
- **Decided by:** Rahul Bharati (maintainer)
- **Context:** 0.3.0's AI layer was the first slice built this way; V0 had landed its spec, tests and code in one commit (`b934920`). No document states this as a rule; it is recorded from the order of the 0.3.0 and 0.4.0 commits.
- **Decision:** A slice begins with a contract commit: the spec in `docs/`, the types, JSDoc'd stubs, and new checks registered but planning nothing (`3a3caab`: "Types, JSDoc'd stubs for app/src/ai, the ai-flow check (registered, plans nothing), a fake LLM server for tests and docs/ai-spec.md"). The next commit adds tests that fail against the stubs (`50bb559`). The implementation follows until they pass.
- **Why:** not recorded.
- **Consequences:** 0.4.0 followed the same order: contracts (`6b9d865`, `fb38d2e`), failing tests ("They fail against the contract stubs until round 2", `7a3232a`), then the implementation merged in two rounds (`9578f2c`, `b7b09b1`); Fernway's acceptance tests were written to fail until Run Hound caught up (`08e94b1`, `693a51b`). The 0.5.0 contract adds a build plan: a foundation step first, then the checks and Fernway in parallel, each step on its own files, then one integration step ([docs/v2-spec.md](../v2-spec.md#build-plan-050), "Build plan (0.5.0)"). 0.5.0 followed it only in part: its contract (`17516ec`) was docs/v2-spec.md alone, with no types or stubs, and its tests landed with the implementation in `7bda95a`.
- **Sources:** commits `3a3caab`, `50bb559`, `6b9d865`, `fb38d2e`, `7a3232a`, `9578f2c`, `b7b09b1`, `08e94b1`, `693a51b`, `17516ec` and `7bda95a`; [docs/v2-spec.md](../v2-spec.md#build-plan-050), "Build plan (0.5.0)".

<a id="2026-09-25-mit-license"></a>
## The core is MIT-licensed, chosen at the public launch instead of the planned Apache-2.0

- **Date:** 2026-09-25
- **Recorded:** 2026-09-26, from commit `ff5422b` ([docs/business-model.md](../business-model.md#licensing), "Licensing")
- **Decided by:** Rahul Bharati (maintainer)
- **Context:** The business model had planned Apache-2.0 for the core (`16630dd`). With 0.3.0 the repository became public (CHANGELOG.md, "0.3.0", "The repository is public").
- **Decision:** MIT for the core: [LICENSE](../../LICENSE), and `"license": "MIT"` in the root, app, Kennel and site `package.json` files.
- **Why:** "Permissive, short and accepted by the companies small teams work at." "MIT was chosen for simplicity." "Since the paid value is hosted, a permissive license is safe."
- **Alternatives considered:** Apache-2.0, "the earlier plan for its patent grant". AGPL "would do more to deter cloud clones, but some companies ban it, which hurts adoption". BSL/FSL: "They are source-available, not OSI-approved open source, and developers notice."
- **Consequences:** Anyone can clone Run Hound, try it and file issues, with no invitation or access request. Paid code, if any, would live in a separate private repository. A CLA or a DCO still has to be chosen "before the first outside contribution" (docs/business-model.md, "Licensing").
- **Sources:** commit `ff5422b`; [docs/business-model.md](../business-model.md#licensing), "Licensing"; [CHANGELOG.md](../../CHANGELOG.md) "0.3.0".

<a id="2026-09-26-tests-isolate-config"></a>
## Tests never read or write the developer's real Run Hound settings in ~/.config/run-hound

- **Date:** 2026-09-26
- **Recorded:** 2026-09-26, from commit `f4fff1e` ([app/test-support/isolate-config.ts](../../app/test-support/isolate-config.ts))
- **Decided by:** Rahul Bharati (maintainer)
- **Context:** "A test wrote ~/.config/run-hound/ai.json with AI on, which then made unrelated CLI and UI tests plan with AI." (`f4fff1e`)
- **Decision:** A Vitest setup file, `app/test-support/isolate-config.ts`, used by the app's and the acceptance suite's Vitest configs, gives every test worker its own empty config folder (`RUNHOUND_CONFIG_DIR` and `XDG_CONFIG_HOME`) and removes the `RUNHOUND_AI*` variables. "Tests can no longer read or write the real config."
- **Why:** so that no test reads or writes the developer's real `~/.config/run-hound/ai.json`, "which would turn AI on for unrelated tests" (the file's comment at `f4fff1e`).
- **Consequences:** 0.4.0 extended it to `accounts.json` and the `RUNHOUND_ACCOUNT*` variables (`ea2ae71`). CLI tests inherit it through the environment of the processes they spawn, and a test that restores the environment afterwards falls back to this folder, never to the real one.
- **Sources:** commits `f4fff1e` and `ea2ae71`; [app/test-support/isolate-config.ts](../../app/test-support/isolate-config.ts); [app/vitest.config.ts](../../app/vitest.config.ts); [tests/acceptance/vitest.config.ts](../../tests/acceptance/vitest.config.ts).

<a id="2026-09-26-account-passwords-stdin-only"></a>
## The command line reads a test-account password from stdin, never from a flag, and passwords are kept out of reports, logs, evidence, specs and AI prompts

- **Date:** 2026-09-26
- **Recorded:** 2026-09-26, from commit `6b9d865` ([docs/v2-spec.md](../v2-spec.md#test-accounts), "Test accounts" and "CLI")
- **Decided by:** Rahul Bharati (maintainer)
- **Context:** V2 (0.4.0) signs in as one of two test accounts the user owns on their app, A and B, so Run Hound has to hold their passwords.
- **Decision:** `run-hound accounts set … --password-stdin` reads the password from stdin, never from a flag; the Settings page and the `RUNHOUND_ACCOUNT_{A,B}_PASSWORD` environment variables, which override the file, are the other ways to set one. "Passwords are **write-only**: never returned by the API, shown in the UI, written to reports, logs, step labels, evidence, specs or AI prompts." Each configured password, and the session values sign-in produces, is registered as a literal secret and redacted wherever it appears, in every encoding. A saved password is bound to the origin of its sign-in page, and `accounts.json` is written with mode 0600 in a 0700 folder.
- **Why:** for stdin: "never a flag, so it stays out of shell history" (docs/v2-spec.md, "CLI"). Otherwise not recorded.
- **Consequences:** Usernames are hidden too, and reports name accounts by label; evidence images are taken with the account's name and session values dotted out; exported specs read the accounts from `RUNHOUND_ACCOUNT_*` variables. The acceptance suite greps the run folders for both passwords (0.5.0 adds the session values and CSRF tokens). A very common password gets a warning, since hiding it everywhere "would give it away". 0.4.1 types the password only on the sign-in page's own origin and stops any request carrying it to another origin (`1223cb5`).
- **Sources:** commits `6b9d865` ([docs/v2-spec.md](../v2-spec.md#test-accounts), "Test accounts" and "CLI"), `ea2ae71` and `1223cb5`; [CHANGELOG.md](../../CHANGELOG.md) "0.4.0" ("Security") and "0.5.0"; [docs/signed-in-runs.md](../signed-in-runs.md).

<a id="2026-09-26-write-side-safety-contract"></a>
## Checks that write change only the run's own test record, decide from a re-read and put the record back

- **Date:** 2026-09-26
- **Recorded:** 2026-09-26, from commit `17516ec` ([docs/v2-spec.md](../v2-spec.md#safety-contract-all-three-checks), "Safety contract (all three checks)")
- **Decided by:** Claude, approved by Rahul Bharati (merged in [PR #6](https://github.com/rahul-bharati/run-hound/pull/6))
- **Context:** The 0.5.0 contract planned three checks that use accounts A and B to test writes (`write-access`, `csrf`, `paywall-trust`): "These three checks change data in account A, so each one follows the safety rules below." In 0.4.0, `mass-assignment` already restored what it changed, and a fix the same day made it put Account A back after a failure too (`847710c`).
- **Decision:** A write targets only a record Run Hound created as A in the same scenario, never A's own records or ids found by listing, guessing or incrementing. Requests go only to the target's origin or the app's local API. Sign-out, password, email, account-deletion, payment or checkout provider, invitation and sharing endpoints are never called, even with `--allow-destructive`. A write "worked" only when a re-read as A shows the change. After each attempt the scenario puts the record back, re-reads it and names anything it couldn't undo, and it is not a pass while such a note stands. Credentials come only from the configured accounts, and evidence redacts cookies, bearer tokens, CSRF tokens and both passwords. These checks are unticked by default.
- **Why:** they change account A's data on purpose. For the verdict rule: "The attempted request's status does not decide it (a `200 {error}`, a write that is ignored, or a `404` from an idempotent DELETE are all common)."
- **Consequences:** `csrf` (0.5.0) follows it; the shared helpers in `app/src/checks/lib/record-state.ts` (`findOwnRecord`, `snapshotRecord`, `rereadRecord`, `restoreRecord`) serve `csrf` and `mass-assignment`; the acceptance suite checks that Alex's and Sam's records read the same afterwards. `write-access` and `paywall-trust` must meet it when they are built.
- **Sources:** commit `17516ec` ([docs/v2-spec.md](../v2-spec.md#safety-contract-all-three-checks), "Safety contract (all three checks)"); commit `847710c` ([PR #5](https://github.com/rahul-bharati/run-hound/pull/5)); [PR #6](https://github.com/rahul-bharati/run-hound/pull/6); [CHANGELOG.md](../../CHANGELOG.md) "0.5.0".

<a id="2026-09-27-site-images-warm-and-preload"></a>
## The site keeps Next's standalone output; tab images are preloaded and the image cache is warmed in the Docker build

- **Date:** 2026-09-27
- **Decided by:** Rahul Bharati (maintainer), choosing between options Claude measured
- **Context:** the maintainer saw tab screenshots (Plan, Run, Report) on the home page arrive late and proposed switching Next's output from `standalone` to the default. Measured on the standalone build: `sharp` is bundled and the optimiser answers 200; a hidden tab's image is lazy, so its request starts only on the click, and the first request for each size encodes AVIF on demand (0.58 s at 1920 px and 1.28 s at 3840 px on a fast desktop; slower on a small server). The installed Next 16.3.5 docs show `next start` uses the same on-demand optimiser, so the output mode changes neither cause.
- **Decision:** keep `output: "standalone"`. The tour loads the next tab's image early at low priority once it is near the screen (after the page has loaded; not with Data Saver), and the other tabs' images once the visitor clicks, hovers or focuses a tab, using each panel's own `<img>` so nothing is fetched twice. - **Why:** it removes both causes: no visitor waits on an encode, and the image is usually there before the click.
- **Alternatives considered:** the default output (same optimiser, larger image); a static export with pre-built images (drops the trailing-slash redirects, `headers()` and the per-page CSP files, and makes pages heavier).

The site image's build warms 1,072 variants in about 37 s and serves them from cache in 1-4 ms. The same pass loads the decorative hound mark and header logo eagerly (desktop LCP down about 600 ms on every page) and brings CLS to 0 with `display: "optional"` for the display font.
- **Sources:** `site/src/components/home/tour.tsx`, `site/scripts/warm-images.mjs`, `site/Dockerfile`, `site/src/app/layout.tsx`; the measurements in the site workflow, 2026-09-27.

- **Context:** the write-side safety contract says a check writes only a record the run itself created. `paywall-trust` can't stay inside it: to catch a success page that grants a paid plan on load (Fernway's V09), the probe has to change Account A's real plan. Of the three probes in the 0.5.0 spec, the client-sent price or plan replay would have to start a checkout, which on a real app reaches the payment provider through the app's server, and no fixture bug proves it; the paid-feature API probe can't see paid-only requests from a free account.

<a id="2026-09-27-form-save-held-before-it-reaches-the-app"></a>
## The write-side checks hold the form's own save in the page and stop one that would change a record Account A already had

- **Date:** 2026-09-27
- **Decided by:** Claude, from the 0.6.0 final review (round 2)
- **Context:** `write-access` and `csrf` create their test record by submitting the form as Account A, and only afterwards could tell that the form edits a record A already had. The review's probe (a "Rename task" form that sends `PATCH` or `POST /api/tasks/t1` for A's own "Groceries") showed A's record left holding the test value, a skip note saying Run Hound "only ever writes to a record it created" although it had just written to that one, and `csrf` forging two more writes at it (stored with a `SameSite=None` cookie, "pass" with a `Lax` one). The safety contract says A's pre-existing records are never written to.
- **Decision:** both checks judge each write the form's submit sends to the app before it leaves the page (a page route, with the context's safety gate still applied after it), until the form's own save (the first write carrying the run's test values) has gone through. A write that isn't a `POST`, or a `POST` whose path, id query or body names a record id the page read before the submit (unless it posts to a path the page read as a list: a create there), or that posts to a path the page read as one record, is stopped, and the scenario is skipped saying so and that nothing was changed. A save that went through and only then shows it changed such a record (the shared `editsExistingRecord`, write-access's old guards moved to `record-state.ts`) is skipped before any other write or forge; the record is put back as the page read it before the save, through the app's own update for its id, and what can't be is named with the form's save and "check Account A".
- **Why:** the only way to never write to A's record is not to let the write reach the app; judging after the save can at best undo it.
- **Alternatives considered:** keep the post-save guards and only fix the note (the record would still be changed, and restores can fail); stop every write whose URL names any id seen before (it would also stop creates under a parent record, `POST /api/projects/p1/tasks`, which the list-read exception keeps).
- **Consequences:** a form that creates through `PUT` or `PATCH`, or posts to a URL naming a record the page read (outside a list it reads), is skipped with nothing written: a missed scenario, never a write to A's data. A save whose URL and body name no record (an upsert) still goes through and is put back afterwards when the app sent an update for the record.
- **Sources:** the review's scratch probes (`edit-probe.mts`, `edit-probe-none.mts`); `app/src/checks/lib/record-state.ts` (`holdExistingEdits`, `changesReadRecord`, `editsExistingRecord`, `putBackEdited`); [docs/v2-spec.md](../v2-spec.md#write-access-amendments).

<a id="2026-09-27-paywall-trust-quiet-reread-and-trials"></a>

<a id="2026-09-28-csrf-reads-the-forges-answer"></a>
## csrf reads the answer to every forge and forges every run-token value

- **Date:** 2026-09-28
- **Decided by:** Claude, from the 0.6.0 final verification
- **Context:** `csrf-forge.test.ts` and `csrf-hold.test.ts` (0.6.0 rounds 1 and 3) were red: the `text/plain` forge's answer was never seen, so a stored one read as "the save needs no session" and a refused one on a single-record read was inconclusive; a hidden token under an unlisted name (sesskey, formToken) was replayed; only the first run-token value was forged, never a nested one or a multipart body; a 303, a 400 and a 2xx that stored nothing were all read as a refusal; a loopback-only CORS allowlist was reported as "any site"; and a GraphQL save that reached the app was skipped without saying so.
- **Decision:** the `text/plain` forge is a `no-cors` fetch, whose answer the network layer reports. The forged body leaves out a random hidden value (`tokenSources`), marks every run-token value at any depth keeping its length, and a multipart save is posted as a multipart form. A 3xx that isn't a redirect to a sign-in page is an answer; a `400` to a forge sent the save's own way that carried A's cookie, with nothing left out, is inconclusive; a 2xx that stored nothing passes without naming a defence. A new record carrying the run's values after an accepted forge is a stored forge. When CORS allows the attacker page, a second preflight from `http://run-hound-other-site.invalid` tells a loopback-only allowlist (an advisory finding) from one that reflects any site. When the saved record can't be read back, the note names the form's own save that reached the app and says to check Account A.
- **Why:** a pass must mean a defence refused the forge, and a finding must name the cookie that rode on it; each of these cases gave the wrong verdict or the wrong words on a small app built in the tests.
- **Alternatives considered:** keep the CORS-mode fetch and read the answer from the server side (Run Hound has no access to the app's server); treat every 4xx with a cookie as inconclusive (ASP.NET answers a missing antiforgery token with 400 and Rails with 422, so a real defence would never pass; the rule applies only to a 400 with nothing left out).
- **Consequences:** a JSON save's CORS check sends one more preflight, to the app only. A forge refused with 400 for its value is not a pass. A new record is counted by the test record's id key, else by count, and only after a forge the app may have taken.
- **Sources:** `app/src/checks/csrf.ts`, `app/src/checks/lib/cross-site.ts`; `app/src/checks/csrf-forge.test.ts`, `app/src/checks/csrf-hold.test.ts`, `app/src/checks/csrf.test.ts`; [docs/v2-spec.md](../v2-spec.md#csrf).

<a id="2026-09-28-csrf-cookies-unknown-when-the-answer-is-unseen"></a>
## csrf says which cookies rode on a forge only when it saw the answer, and never forges a body it can't rebuild as named fields

- **Date:** 2026-09-28
- **Decided by:** Claude, from the 0.6.0 release review (close-out)
- **Context:** the close-out found three `csrf` gaps. A forge the app answered after the 5-second wait had no Cookie header to read: Playwright attaches the Cookie header a request really carried to `allHeaders()` only when its answer arrives, so an empty list read as "no cookie" and a stored forge was titled "(the save needs no session)". A native form post leaves the page, and the page it lands on may hold no copy of the token the save carried, so a hidden token under a name no list knows was replayed. A save whose body is a JSON array was skipped with a false reason. The contract's `csrf` "Cookies" rule also said the forge waits out Chromium's 2-minute window for a new `Lax` cookie, which no release did.
- **Decision:** `ForgeOutcome.cookiesSeen` says whether the cookies were read with the answer. An unseen answer means the cookies aren't known, never "no cookie": "(the save needs no session)" is claimed only for a forge seen with none; a stored unseen forge is a confirmed "(no CSRF protection)" finding that says the cookies aren't known, and its fix also asks to make sure the save requires the session. The page's anti-CSRF token values are read before the form is filled and again after the submit, and both sets are left out. A JSON array, a bare JSON value or a multipart body carrying a file is not forged: the scenario is skipped with a note that names the body type. Only a `400` to a forge that carried A's cookie, sent the save's own way with nothing left out, counts as refusing the value; `409` and `422` stay refusals. The spec's "Cookies" rule now says that every forge is posted into a frame or sent as a fetch, never a top-level navigation, so the 2-minute window never applies.
- **Why:** a finding may name what rode on a forge only when Run Hound saw it, and a token the page held before the submit is still Account A's token.
- **Alternatives considered:** forge JSON arrays too (the exported spec rebuilds the body as an object from its named fields, so it would ship a wrong spec); count a `422` or `409` as refusing the value like a `400` (Rails answers a missing CSRF token with `422`, and the capture records no request headers that would tell a header-token save apart, so a real defence would never pass); wait longer for the answer (a slower app always exists); copy the existing-record hold into `csrf.ts` to cover GraphQL (it would split the hold `csrf` and `write-access` share and leave `write-access` open).
- **Consequences:** known limits in TESTING.md and [Signed-in runs](../signed-in-runs.md): a token the app's scripts keep in memory and send under another name is replayed; array, bare-value and file bodies are skipped; an app that rejects the forged value itself with `422` or `409` passes; a slow app's stored forge says the cookies aren't known. Two must-fixes from the review stay open outside `csrf.ts`, for an owner of `write-access.ts` and `record-state.ts`: `write-access` passes an app whose update carries an anti-CSRF token in a header (`X-CSRFToken`), and the existing-record hold learns no ids from a GraphQL `POST` read. The lenient GraphQL case in `csrf-hold.test.ts` is to be tightened with that fix.
- **Sources:** `app/src/checks/csrf.ts` (`unforgeable`, `forgedCard`), `app/src/checks/lib/cross-site.ts` (`ForgeOutcome.cookiesSeen`); `app/src/checks/csrf-unseen.test.ts`, `app/src/checks/csrf-native-post.test.ts`, `app/src/checks/csrf-array-body.test.ts`; [docs/v2-spec.md](../v2-spec.md#csrf).

<a id="2026-09-28-write-access-stale-version-refusals-inconclusive"></a>
## write-access treats a refusal of a version it couldn't refresh as inconclusive, and the save is found in a form-encoded body

- **Date:** 2026-09-28
- **Decided by:** Claude, from the 0.6.0 release review (close-out)
- **Context:** round 1 made `write-access` send each version or lock stamp at its value in the re-read before the attempt, and made a `409`, `412` or `428` on an unchanged record inconclusive. The close-out's optimistic-locking variants found apps that refuse a stale version with a `400`, a `422` or an unhandled error (Rails' `StaleObjectError`), and records whose reads don't show the stamp at all, so Run Hound could only send the stale value the app's own update carried, and the refusal read as a pass. Separately, `findOwnRecord` looked for the save only in a body that held the typed value as it is, so a form-encoded save (`title=Task+rs7…`) wasn't found, and a read made while Run Hound typed (a name-availability check echoing the value) could be taken for the test record, skipping an ordinary create form with a false "changed a record Account A already had".
- **Decision:** `withFreshStamps` names the stamps the re-read doesn't show (`Write.staleStamps`). An attempt that left the record unchanged and was answered `400`, `422` or `5xx` while it carried one of them is inconclusive, never a pass. A `401`, `403` or `404` is judged as before, and a `400`, `422` or `5xx` still passes when every stamp could be refreshed, so clean apps keep passing. `findOwnRecord` finds the save in a form-encoded body too (`bodyHolds`), so a read made before it is never the record endpoint. An update guarded by `If-Match` is a documented limit.
- **Why:** a pass has to mean the app refused the sender, not a stale version Run Hound had no way to refresh.
- **Alternatives considered:** make every `400`, `422` or `5xx` on an unchanged record inconclusive (a clean app that validates the replayed body would never pass); treat a path segment holding the typed value as an echo (it would drop real records read at a slug equal to a test value, such as `/api/users/<login>`); keep request headers in the capture to handle `If-Match` (`CapturedRequest` keeps none, a change beyond the close-out).
- **Consequences:** `write-access` replays none of the app's update headers: an `If-Match` update is inconclusive on `412` or `428` and a pass on another status (a known limit). JSON saves, and `write-access`, which passes its save explicitly, find the record as before.
- **Sources:** `app/src/checks/write-access.ts` (`withFreshStamps`, `mayRefuseStale`), `app/src/checks/lib/record-state.ts` (`bodyHolds`, `findOwnRecord`); `app/src/checks/write-access-stamps.test.ts`, `app/src/checks/lib/record-state-echo.test.ts`; [docs/v2-spec.md](../v2-spec.md#write-access-amendments).

<a id="2026-09-28-paywall-trust-quiet-read-before-the-next-page"></a>
## paywall-trust reads the plan once more, after a quiet wait, before it opens the next page, and the docs say page-controls may click a plan button

- **Date:** 2026-09-28
- **Decided by:** Claude, from the 0.6.0 release review (close-out)
- **Context:** a grant that lands late (a queued job) was credited to whichever route was open next, even one that answered 404, and the exported spec replayed that route; when the next route was a catch-all showing the page under test, the grant was lost as drift. Separately, TESTING.md, the guides, the spec, the roadmap, the CHANGELOG and [the 2026-09-27 entry](09-2026.md#2026-09-27-paywall-trust-changes-and-restores-the-plan) said `paywall-trust` is the only check that clicks a cancel or downgrade control and that such buttons are never clicked while signed in. `page-controls`, ticked by default, clicks a plan button whose name isn't on the destructive list ("Switch to Free", "Choose Pro", "Start free trial") on any run, and "Cancel subscription" with destructive scenarios allowed, signed in too.

Known limits: a grant that lands more than about 5 s after its route is put down to a later route or, after the last quiet read, not seen; a page under test that is itself a success page granting on load grants before the first read and passes. The 2026-09-27 entry's "(the only check allowed to click one …)" is corrected by this one; `paywall-trust` still clicks such a control only to undo its own change.
- **Sources:** `app/src/checks/paywall-trust.ts` (`quietBeforeNext`, `scanLinks`'s `before`); `app/src/checks/paywall-trust-shapes.test.ts` ("is never credited to the next page when that page answered too", "is never credited to the next Billing tab chosen"); `app/src/checks/dead-control.ts` (`DESTRUCTIVE_NAME`, `SESSION_ENDING_NAME`); [docs/v2-spec.md](../v2-spec.md#paywall-trust-amendments).
- **Supersedes:** the claim in [paywall-trust may change Account A's plan …](09-2026.md#2026-09-27-paywall-trust-changes-and-restores-the-plan) that it is the only check allowed to click a cancel or downgrade control (the rest of that decision stands)

<a id="2026-09-28-sessionstorage-seeded-only-when-the-session-lives-there"></a>
## sessionStorage is seeded only when the session lives there

- **Date:** 2026-09-28
- **Decided by:** Claude, from the 0.6.0 release review (rounds 1 and 2, and the close-out)
- **Context:** seeding every sessionStorage item into every context of the identity made a cookie-session app that caches its reads in sessionStorage load pages from that copy. `access-control` then had no data read to replay and missed an IDOR that 0.5.0 caught, and a workspace id the app kept there was redacted from report locations and specs. Deciding by cookie names missed `.AspNetCore.Cookies`, `app_user` and custom express-session names.
- **Decision:** sessionStorage is returned and seeded only when one of its values was sent in a credential header after the password was typed (never a CSRF header), or when the session is nowhere else. It is somewhere else when there is a token-like cookie the submit set or changed (whatever its name), a session-named cookie or an HttpOnly cookie of the app's own site holding a token, or a localStorage or IndexedDB token; CSRF, analytics, bot-check, load-balancer and bot-manager cookies never count. Otherwise sessionStorage values are registered by localStorage's rules, and values the app's own requests carried in a path or a query are ids, never secrets.
- **Why:** the access checks must see the app's own data reads, and a copy of a read cache hides them.
- **Alternatives considered:** always seed (the missed IDOR); decide by cookie names alone (the cookie sessions above were missed); open a cookie-only tab after sign-in to see whether it is signed in (more reliable, but it means another page load of the app during sign-in).
- **Consequences:** a sessionStorage session that sends nothing with its token while signing in, next to an HttpOnly cookie of its own site that isn't a known load-balancer or bot-manager cookie, is taken for a cookie session and not seeded, and the plan fails with "still shows the sign-in page".
- **Sources:** `app/src/engine/auth.ts` (`sessionInStorage`, `sessionCookieSet`, `NOT_SESSION_COOKIE`); `app/src/engine/auth-sessionstorage-role.test.ts`, `app/src/engine/auth-cookie-session-kept.test.ts`; [docs/v2-spec.md](../v2-spec.md#sign-in-two-step-and-sessionstorage-060).

<a id="2026-09-28-code-step-by-heading-needs-a-code-field"></a>
## A code step named only by the page's heading needs a field that looks like a code's, and the app's own site is read without a public-suffix list

- **Date:** 2026-09-28
- **Decided by:** Claude, from the 0.6.0 release review (close-out)
- **Context:** the round-3 code-step rule took a sign-in code word in the page's headings or title as enough, so a signed-in landing page with "Verify your email" above a "New task" field, a page titled "Identity verification" whose field finds a customer, or a two-factor set-up page's phone field failed sign-in with "asks for a verification code". The new HttpOnly-cookie rule of the [sessionStorage decision](09-2026.md#2026-09-28-sessionstorage-seeded-only-when-the-session-lives-there) needs the app's own site, and Azure App Service sets its `ARRAffinity` load-balancer cookie HttpOnly by default.
- **Decision:** a code word in the field's own name, label or placeholder still decides on its own. When only the headings or the title name a code step, the single field must look like a code's: code, OTP, PIN, token or digit in its own words, `inputmode` numeric or decimal, a `maxlength` of 4 to 8, or a code split over one-character boxes. The broad name match at the sign-in page's own address (a field that says code or verify) stays as it has been since 0.4.0. The app's own site is the last two labels of the sign-in page's or the landing page's host name, or the same IP address or one-label host (`siteOf`), and the load-balancer and bot-manager cookies (`ARRAffinity`, `AWSALB`, `GCLB`, `ak_bmsc`, `_abck`, `visid_incap_`, `incap_ses_`, `BIGipServer`, `TS01…`, `NSC_`, `datadome`, `_px…`, `INGRESSCOOKIE`, `ROUTEID`) never count as the session.
- **Why:** an ordinary landing page must sign in, and a real one-time-code page still fails with the code message.
- **Alternatives considered:** narrow the match at the sign-in page's own address too (it could miss an OTP field shown next to a password field that is still visible); a public-suffix list (a new dependency, which the close-out can't add).
- **Consequences:** known limits: a code page whose only field says nothing of a code, named a code step only by its heading, isn't recognised (Test sign-in reports success); an app that shows its signed-in view at the sign-in page's address with a "Room code" field fails with the code message. On a two-label public suffix such as `co.uk`, `siteOf` may count another site's HttpOnly cookie as the app's, which errs toward a cookie session.
- **Sources:** `app/src/engine/auth.ts` (`showsCodeStep`, `siteOf`, `NOT_SESSION_COOKIE`); `app/src/engine/auth-next-page-steps.test.ts`, `app/src/engine/auth-cookie-session-kept.test.ts`; [docs/v2-spec.md](../v2-spec.md#sign-in-two-step-and-sessionstorage-060).

<a id="2026-09-28-hold-learns-graphql-reads"></a>
## The existing-record hold learns ids from GraphQL reads sent as POSTs, and stops a GraphQL save that doesn't say it creates a record

- **Date:** 2026-09-28
- **Decided by:** Claude, from the 0.6.0 release review (close-out, round 1)
- **Context:** the hold judged the form's save only against the page's `GET` reads. A GraphQL app built on Apollo Client reads with `POST /graphql`, so the hold learned no ids, and the form's `updateTask(id: "t1", …)` mutation renamed Account A's own task `t1` while `write-access` was skipped with "couldn't read the saved record back" and no "check Account A". The close-out had left this open for an owner of `record-state.ts` (see [csrf reads the answer to every forge](09-2026.md#2026-09-28-csrf-reads-the-forges-answer)). A GraphQL save with no id at all (`updateProfile(name: …)`) would have gone through the same way even with the ids learned.
- **Decision:** a POST whose body is a GraphQL query (no mutation; `isGraphQlRead`, now shared in `core/saves.ts`) is a read: never stopped, and its answer counts with the GETs' for the ids it holds. A GraphQL read's path (`/graphql`, a POST read or a GET with `?query=`) is never taken for a list or a record the page read, since one endpoint serves every operation. A mutation naming a read id in its variables (as before) or as a literal argument in its query text is stopped. Before any save has gone through, the form's GraphQL mutation whose root fields don't all read as a create (a create verb first, or create, add or insert last, and no word that says it changes one: `createTask`, `taskCreate`, `insert_tasks_one`, `addComment` do; `updateProfile`, `saveSettings`, `upsertTask`, `likePost` don't; a persisted query by its operation name) is stopped too, with its own note. The hold's re-read after a stopped save sends a GraphQL read again with the query body the page sent. `write-access`, like `csrf`, names the form's save and says "check Account A" when it can't read the record back after the save reached the app. The lenient GraphQL case in `csrf-hold.test.ts` now requires the mutation to be stopped.
- **Why:** the safety contract says A's pre-existing records are never written to, and a GraphQL save may change one without naming it; a check can't read a GraphQL record back anyway (no `GET`), so stopping an unclear mutation costs no coverage.
- **Alternatives considered:** take every GraphQL read's path as a record the page read (stops every mutation, a create too, with a note that falsely says it changes a record A already had); learn ids from every POST answer before the save (a mutation's answer may name records it just created); read the record back through the app's own GraphQL query (a new read path for one kind of app, left for later).
- **Consequences:** on a GraphQL app that reads with `POST /graphql`, `write-access` and `csrf` are skipped (known limit); a create mutation reaches the app and the note says to check Account A. After a save has gone through, a later mutation is judged only by the ids it names, and a persisted query with no operation name is stopped as "a persisted query".
- **Sources:** `app/src/checks/lib/record-state.ts` (`holdExistingEdits`, `readBeforeSave`, `mutationFields`, `unclearGraphQlSave`, `graphQlLiterals`, `readRecordChanged`); `app/src/core/saves.ts` (`isGraphQlRead`); `app/src/checks/write-access.ts`; `app/src/checks/lib/record-state-graphql.test.ts`, `app/src/checks/write-access-graphql.test.ts`, `app/src/checks/csrf-hold.test.ts`; [docs/v2-spec.md](../v2-spec.md#write-access-amendments).

<a id="2026-09-28-write-access-header-csrf-tokens"></a>
## write-access sends the identity's own anti-CSRF token in a header the app's update carried

- **Date:** 2026-09-28
- **Decided by:** Claude, from the 0.6.0 release review (close-out, round 1)
- **Context:** Django, Laravel and Rails apps send their anti-CSRF token from scripts in a header (`X-CSRFToken`, `X-XSRF-TOKEN`, `X-CSRF-Token`). `write-access` replayed the update's body without it, so Account B's replay was refused with `403` by the CSRF check and read as a pass on an update with no ownership check: a missed critical finding with no warning. The capture kept no request headers, and `CheckContext.request` dropped every `x-*-token` header a caller passed.
- **Decision:** the capture keeps a write's anti-CSRF headers (a name with csrf or xsrf in it; `isAntiCsrfHeader`) for requests to the app, in memory. `write-access` puts the identity's own token in each: read where Account A's came from (the csrf/xsrf cookie or `<meta>` whose value, as it is or URL-decoded, is A's) on a page opened as B, decoded the same way. `CheckContext.request` sends an anti-CSRF header a caller passes (it names no one; the session does); every other credential header is still only the identity's own. A's token is never sent in a header as someone else: with none of B's own to read, and always signed out, the header is left out, and a `403` or `419` to that attempt is inconclusive, never a pass (a body token that can't be swapped stays A's, as before).
- **Why:** the refusal must come from the app's ownership check, not from a CSRF token the replay couldn't carry.
- **Alternatives considered:** treat every `403` to a replay that dropped a header token as inconclusive without sending B's token (true, but it would leave such apps untested); send A's token as B (it would make B's request partly A's, against the rule that an identity's credentials are its own).
- **Consequences:** a token the app's scripts keep in memory (fetched from an API) has no B value to read, so those apps are inconclusive on a `403`. Other headers (`If-Match`) are still not replayed (known limit). The exported spec names the header and says to add B's own token. B's token is read from a page opened as B while the replay carries B's saved session cookies, so an app that gave B a new csrf cookie on that page load, and checks the header against the cookie sent, would refuse the replay and it would read as a refusal (Django keeps the cookie it set at sign-in; Laravel accepts any token it issued for the session).
- **Sources:** `app/src/engine/capture.ts`, `app/src/engine/context.ts`, `app/src/core/saves.ts` (`isAntiCsrfHeader`); `app/src/checks/write-access.ts` (`withOwnHeaderTokens`); `app/src/checks/write-access-header-token.test.ts`, `app/src/engine/capture-csrf-headers.test.ts`, `app/src/engine/context-request.test.ts`; [docs/v2-spec.md](../v2-spec.md#write-access-amendments).

<a id="2026-09-28-graphql-read-needs-a-graphql-query"></a>
## The existing-record hold takes a POST for a GraphQL read only when its body is a GraphQL query, and judges a GraphQL mutation by its name after the form's create too

- **Date:** 2026-09-28
- **Decided by:** Claude, from the 0.6.0 release review (close-out, round 2)
- **Context:** round 1 shared `isGraphQlRead` (a JSON body whose operations each have a string `query` without the word "mutation") and let a POST that passed it through the existing-record hold unjudged. The round-2 review found that a REST edit form whose body has a `query` field passed that test: after `GET /api/searches/s1` or `GET /api/settings`, a saved search's `{name, query}` (at `/api/searches/s1`, or at `/api/searches` with `id: "s1"`) and a default-search setting's `{query}` reached the app and changed Account A's record, under `write-access` and `csrf` alike, where 656f158 had stopped all three. It also found that after the form's create went through, a later mutation carrying the typed value was judged only by the ids it named, so `updateProfile(name: …)` after `createTask` reached the app, and that `submitProfile` read as a create because `submit` leads it.
- **Decision:** `isGraphQlRead` (`core/saves.ts`) asks for a GraphQL request: each operation holds only `query`, `variables`, `operationName` and `extensions`, and its `query`, with comments and strings left out, starts a GraphQL document (`isGraphQlDocument`: a selection set, or `query`, `subscription` or `fragment` before one) that holds no mutation. The hold, the ids it learns, the query body its re-read sends again and the test-record count (`isAcceptedSave`) all use it, and the hold's check of a GraphQL read made as a GET uses the same document test. After a save has gone through, a mutation carrying the test values whose name doesn't read as a create is stopped unless it names an id the page hadn't read before the save that the save's own answer held: the record it created (Relay's `clientMutationId` names none). A create verb before the one record of its kind an account has (`profile`, `settings`, `setting`, `preferences`, `preference`, `prefs`, `account`, `me` or `viewer` as the thing made: `submitProfile`, `sendSettings`, `accountCreate`) doesn't read as a create; `createProfileNote` still does.
- **Why:** the safety contract says Account A's pre-existing records are never written to, and the loose test let the form's own save past the hold.
- **Alternatives considered:** also refuse a GraphQL read whose path the page read as a REST record (defence in depth, but a real GraphQL endpoint is never read that way, and the body test stops every shape found); take any id the page hadn't read as the new record, as the review suggested (an unread `userId`, or a `clientMutationId`, would let `updateProfile` through); stop every mutation after a save that doesn't read as a create (the app's own `updateTask` for the task it just created would skip the form).
- **Consequences:** a REST save with a `query` field is judged like any other save and is counted as a test record. A GraphQL read that carries another key beside those four, or nested parentheses in its variable definitions, is judged like a write: it goes unless it names a record the page read, and its answer isn't learned as a read. A mutation such as `createBankAccount` or `addViewer` reads as unclear, so the scenario is skipped with the GraphQL note, and so is a form whose create is followed by another mutation carrying the typed value that names no new record (an activity log such as `trackEvent`). A later unclear mutation waits up to 2 s for the capture to read the save's answer.
- **Sources:** `app/src/core/saves.ts` (`isGraphQlRead`, `isGraphQlDocument`, `graphQlCode`); `app/src/checks/lib/record-state.ts` (`holdExistingEdits`, `graphQlGet`, `createsRecord`, `SINGLETON_NOUNS`, `graphQlIds`); `app/src/core/saves.test.ts`, `app/src/engine/accepted-saves.test.ts`, `app/src/checks/lib/record-state-query-key.test.ts`, `app/src/checks/lib/record-state-graphql.test.ts`; [docs/v2-spec.md](../v2-spec.md#write-access-amendments).
- **Supersedes:** in part, [The existing-record hold learns ids from GraphQL reads sent as POSTs …](09-2026.md#2026-09-28-hold-learns-graphql-reads): its test for a GraphQL read, and its consequence that after a save has gone through a later mutation is judged only by the ids it names (the rest of that decision stands)

<a id="2026-09-28-write-access-token-refusals-400-422-and-header-pairing"></a>
## write-access counts a 400 or 422 to a replay without the app's anti-CSRF token as a possible CSRF refusal, and pairs a header with its usual source when A's value has changed

- **Date:** 2026-09-28
- **Decided by:** Claude, from the 0.6.0 release review (close-out, round 2)
- **Context:** round 1 made a `403` or `419` to a replay that left the anti-CSRF header out, or kept Account A's body token, inconclusive. The round-2 review found that Rails answers a bad token with `422` (`InvalidAuthenticityToken`) and ASP.NET Core's antiforgery with `400`, so a signed-out replay on an app that checks the token first, and Account B's replay with no token of its own on an update with no ownership check (a real IDOR), read as passes. It also found that Laravel encrypts its `XSRF-TOKEN` cookie anew on every answer, so the cookie on A's page never equals the value A's update carried: B's token wasn't sent, a planted IDOR ended inconclusive (`419`), and the note said Run Hound couldn't read B's token though B's cookie was there.
- **Decision:** a write that left out an anti-CSRF header or kept A's body token and was refused with `400`, `403`, `419` or `422` (`TOKEN_REFUSALS`) is inconclusive, never a pass. When no source on A's page holds a header's value, the header is paired with its usual source by name (`HEADER_SOURCE`): `X-XSRF-TOKEN` with the `XSRF-TOKEN` cookie, URL-decoded; `X-CSRFToken` with the `csrftoken` cookie; `X-CSRF-Token` with `<meta name="csrf-token">`; and B's current value goes. The note says Run Hound couldn't match a token of B's own to the one A's request carried, and for a signed-out visitor that it has none of its own.
- **Why:** a pass has to mean the app refused the sender, not a CSRF check that refused a token Run Hound couldn't carry.
- **Alternatives considered:** make every `4xx` to a replay without the token inconclusive (a `401` or `404` is how an ownership check answers, so a clean app would never pass); pair by name first (a match by value is exact, a name only a convention).
- **Consequences:** a replay without the token that the app refuses with `400` or `422` for another reason (a body it doesn't accept) is inconclusive, never a pass, as a signed-out one always is on such an app. An app that reads the header from another source than its usual one, and changes the value on every answer, still leaves B's replay without it (inconclusive). A body token is still swapped only by its value or a hidden input's name.
- **Sources:** `app/src/checks/write-access.ts` (`TOKEN_REFUSALS`, `HEADER_SOURCE`, `withOwnHeaderTokens`); `app/src/checks/write-access-header-token.test.ts`; [docs/v2-spec.md](../v2-spec.md#write-access-amendments), TESTING.md, [Signed-in runs](../signed-in-runs.md).
- **Supersedes:** in part, [write-access sends the identity's own anti-CSRF token in a header the app's update carried](09-2026.md#2026-09-28-write-access-header-csrf-tokens): its "a `403` or `419` to that attempt is inconclusive" (now `400`, `403`, `419` or `422`) and its pairing by value alone (the rest of that decision stands)
