# Signed-in runs and access checks (V2 preview)

This page covers testing pages behind a sign-in as test accounts you own, the V2 checks that run signed in (the access checks and the write-side checks), the sign-in forms Run Hound handles, and what sign-in can't do yet.

Pages behind a sign-in can be tested signed in, as one of two test accounts **you own** on your app: A and B. Run Hound signs in with a fresh session at the start of each plan and run, and every check then runs signed in. Six V2 checks join the plan: three from 0.4.0, and three write-side checks that change account A's data on purpose and put it back (`csrf` from 0.5.0, `write-access` and `paywall-trust` from 0.6.0):

| Check | What it asks | Planned |
|---|---|---|
| `access-control` | Signed in as A, Run Hound finds A's data on the page. Can account B read it? Can a visitor who isn't signed in? | Signed in. The account B scenario only when B is set up and "A and B must not see each other's data" is on. Ticked. |
| `mass-assignment` | Does the server store `role`, `isAdmin`, `plan`, `credits`, `verified` and similar fields that the form never sends? | Signed in, for each form that saves (it needs a JSON save request, and skips with the reason otherwise). **Unticked**: it changes account A, then restores it. |
| `deep-links` | Do the app's own pages load when opened directly (a reload, a shared link)? | When the page links to other pages of the app, signed in or not. Ticked. |
| `csrf` (0.5.0) | Can a page on another site make A's browser change A's data (no CSRF token, no Origin check, a session cookie sent cross-site)? | Signed in, for each form that saves a record. **Unticked**. |
| `write-access` (0.6.0) | Can account B, or a visitor who isn't signed in, change or delete A's records, with the update and delete requests the app itself sends? | Signed in, for each form that saves a record; the account B scenario as for `access-control`. **Unticked**. |
| `paywall-trust` (0.6.0) | Can A get a paid plan without paying, by opening the app's own success, upgraded or thank-you page? | Signed in, once per page (skipped when the page reads no plan of A's, or A is already on a paid plan). **Unticked**. |

What they never do:

- `access-control` replays only the read requests (GET) that returned A's data on this page, as B and with no session. It never replays a path that acts (`/logout`, `/unsubscribe`), and each of its two scenarios saves at most one test record as A, through a form that saves a record, so it has data to look for. When it finds none, it is skipped with the reason.
- `mass-assignment` saves the form as A, sends the same save once more with the extra fields, reads the record back, then saves the original values again. Its notes say what came back, what the server kept, and what it couldn't restore (a field that wasn't there before can't be removed: check account A).
- `deep-links` opens at most 10 of the page's own links, each in a fresh browser, and never a link that acts when opened: sign out, delete, unsubscribe, disconnect, accept an invitation, `?action=delete`.

**The write-side checks** (`csrf`, `write-access`, `paywall-trust`) follow the same rules:

- They write only the test record Run Hound created as A **in the same scenario** (never one of A's own records, never an id found by listing or guessing), and only to your app's own origin or its local API. The one exception is `paywall-trust`, which may change A's plan (plan, role, credits, entitlements) and nothing else.
- They never call sign-out, password, email, account-deletion, payment-provider, invitation or sharing endpoints, even with `--allow-destructive`.
- A write counts as working only when a re-read as A shows it, never from a status code.
- Afterwards they put it back, re-read, and name anything they couldn't undo ("check Account A"); a scenario is never a pass while such a note stands.

How each one works:

- `csrf` sends the forged request from a real browser page on another site (`127.0.0.1` for a `localhost` app, and the other way round), so the browser attaches only the cookies it would for any website; only requests a web page can send without a CORS preflight are forged (form-encoded, multipart or `text/plain`), plus the JSON itself when the app's CORS answer to a real preflight allows the other site with credentials (a finding also noted as `cors`, advisory when CORS trusts only loopback origins). On any other host name (a private name from `RUNHOUND_ALLOWED_HOSTS`, `host.docker.internal`) no cross-site origin can be set up and the scenario is **inconclusive**, never a pass. Point it at `http://localhost:<port>` or `http://127.0.0.1:<port>`. On an app that sends its session as a bearer token rather than a cookie (sessionStorage or localStorage), it reads the record back with the credential headers the app's own scripts send, and passes: no cookie rides along, so there is nothing for another site's page to use, unless the save needs no session at all (then the finding says "the save needs no session", and its fix is to require the session first). "The save needs no session" is said only when Run Hound saw the app's answer to the forge and the request carried no cookie. It waits up to 30 seconds for each answer; with none, a stored forge is still a confirmed finding, and it says the cookies aren't known, while a forge that stored nothing is **inconclusive**, never a pass (the app may still store it: check Account A). A random hidden value Run Hound can't place as a token (a token, or a reference such as a list's id) is left out, and a forge refused in a way a missing value explains (`400`, `404`, `409`, `422`, a `5xx`, a success that stored nothing, or a `403` when the value looks like a reference) is then inconclusive too.
- `write-access` saves a test record as A, then sends the update and delete requests **the app itself sent** for that record after saving it (never a guessed endpoint) as account B, or with no session, each with one field set to a new test value; a `DELETE` goes last, and only when the app sent one. A change or a deletion that A's re-read shows is a critical finding. Each request carries the version or lock the record holds now (`lock_version`, `version`, `__v`, `_rev`, `etag`, `updatedAt`); a version conflict (`409`, `412`, `428`), or a `400`, `422` or `5xx` to a request that had to carry a version the record's reads don't show, is inconclusive, never a pass. A `404`, or a success that changed nothing, to such a request is compared with the same update sent as A with A's own test value (put back afterwards, never a `DELETE`): it passes only when the app applies A's copy or answers it with a conflict. A version in the URL query is refreshed only when the record showed that value, and a request that got no answer is inconclusive. When the app sent no update or delete for the new record while the page was open, the scenario is skipped with that reason: Run Hound doesn't open edit dialogs or row menus to make one. An update sent as a Supabase (PostgREST) filter (`?id=eq.<id>`) isn't recognised as the test record's, so on a Supabase app the scenario is skipped. An anti-CSRF token the app sends in a header (`X-CSRFToken`, `X-XSRF-TOKEN`, `X-CSRF-Token`) goes as B's own, read from the same cookie or `<meta>` on a page opened as B, never as A's; with none to read, a `400`, `403`, `419` or `422` is inconclusive. A form that edits a record A already had is skipped with its save stopped before it reaches the app; on a GraphQL app the ids come from its `POST /graphql` reads too, and from persisted-query reads (a hash or a Relay `doc_id`, which are never sent again), and a mutation whose name doesn't say it creates a record (`updateProfile`), or a Relay save with no name, is stopped as well.
- `paywall-trust` reads A's plan from the page's own requests (`plan`, `tier`, `subscription`, `isPro`, `pro`, `credits`, `entitlements`, `features` or `role` in a JSON answer that names the signed-in account by the email or username it signs in with), then opens up to 10 of the app's own success, upgraded and thank-you pages as A (the page's links, its billing and settings pages' links, then common paths such as `/checkout/success`), with every request to a payment provider blocked, and reads the plan again after each; after each page or Billing tab that loads, it waits until 5 s have passed since that re-read, with nothing opened, and reads the plan once more before opening the next one (up to 5 s more per page), so a change that lands late is put down to the page that caused it. The page under test counts as the first page: a change seen 5 s after the first read (a job its own load queued) ends the scenario inconclusive before anything is opened. A Billing tab's page stays under the tab's hold until Run Hound leaves it for a blank page, so a late request from it to a checkout or portal start never reaches the app, and a run that runs out of time before it opens every page is inconclusive. A plan read only from a sign-in session endpoint (NextAuth's `/api/auth/session` with JWT sessions) may keep the plan A signed in with, so unless it shows a gain the scenario then ends inconclusive, never a pass ("check Account A"). A gain (a paid plan A didn't have, `isPro` turning true, more credits, or more entitlements or features) is a critical finding, "Account A got a paid plan without paying"; any other change (credits a page spent, a free plan moved to a trial, a role) is inconclusive, never a pass or a finding, and the notes name it. A page's own requests (a fetch, an image) are blocked only for the payment providers Run Hound knows (Stripe, PayPal, Paddle, Lemon Squeezy and about 40 more); every page load that leaves the app is stopped. Run Hound never enters payment details. To put the plan back it clicks the app's own cancel or downgrade control ("Cancel plan", "Downgrade", "Switch to Free"), as A, only to undo its own change (`page-controls` and `dead-control`, ticked by default, may also click a plan button such as "Switch to Free" as A, outside or inside a form, and with destructive scenarios allowed a "Cancel subscription"). Replaying a checkout with a changed price and calling paid-only APIs aren't in 0.6.0.
- On a page with a form that edits A's profile, run `paywall-trust` on its own: `axe-states` and `pii-leak` save a test address over A's email first (a limit below), and it then can't tell A's plan; `deep-links` may also open a success page that moves A to a paid plan before it runs.

**"A and B must not see each other's data"** (on by default) is your statement that A and B are different users, not teammates in one workspace. Only then does B reading or changing A's data count as a bug, so the account B scenarios are planned only when it is on.

**Web UI:** **Settings → Test accounts**: for each account, the sign-in page URL, username and password, then **Save** and **Test sign-in**. New Run → **Sign in as**.

**Command line** (from source, in `app/`; in the test lab, start each line with `docker compose -f run-hound.compose.yml run --rm run-hound` instead of `pnpm exec tsx src/cli.ts`):

```sh
pnpm exec tsx src/cli.ts accounts set a --login-url http://localhost:5173/login --username alex@example.test --password-stdin
pnpm exec tsx src/cli.ts accounts set b --login-url http://localhost:5173/login --username sam@example.test --password-stdin
pnpm exec tsx src/cli.ts accounts test          # signs in as each account and says where it landed
pnpm exec tsx src/cli.ts accounts status        # what is set, and where each value comes from
pnpm exec tsx src/cli.ts run http://localhost:5173/app --as a --approve all
```

`--password-stdin` asks for the password without showing it, or reads it from a pipe (`printf '%s\n' "$PASSWORD" | … accounts set a --password-stdin`); a password is never taken from a flag, so it stays out of your shell history. `--approve all` includes `mass-assignment` and the write-side checks. To try it on the test lab's Fernway app: accounts `alex@fernway.test` (A) and `sam@fernway.test` (B), sign-in page `http://fernway-bugs:4110/login`, target `http://fernway-bugs:4110/app`; the passwords are in [fixtures/fernway/README.md](../fixtures/fernway/README.md#accounts). [TESTING.md](../TESTING.md#signed-in-runs-and-access-checks-v2-preview) walks through it, including Fernway's two-step and sessionStorage sign-in modes.

**Secrets.** Accounts are saved next to the AI settings (`accounts.json`, mode 0600, in a 0700 folder; in the test lab that is `./runs/.config/accounts.json`); `RUNHOUND_ACCOUNT_A_LOGIN_URL`, `…_USERNAME`, `…_PASSWORD`, `…_LABEL` (and `_B_`) and `RUNHOUND_ACCOUNTS_ISOLATED` override them field by field. The API and the UI never send a saved password back. A saved password is only sent to the site (origin) it was saved for: move the sign-in page to another site and it has to be entered again. Passwords, session cookies and tokens (sessionStorage tokens included) never appear in reports, evidence, specs, logs, progress or AI prompts, and neither do usernames; reports name accounts by their label. Evidence screenshots are taken with the account's name and session values dotted out; the live view is not masked (it stays on your machine).

**Sign-in forms that work:**

- **One page**: a username (or email) field and a password field in one form. Run Hound fills both and submits.
- **Email first, then the password** (0.6.0): a form that asks only for the email or username, with **Continue** or **Next**. Run Hound fills it, continues, and types the password once a password field shows, on the same page or on the next page on the sign-in page's own site (the same origin). It never types into a sign-up form, and the password is only typed on the site of the sign-in page it was saved for.
- **The session**: cookies, localStorage and IndexedDB (Supabase and Firebase keep it there), and (0.6.0) sessionStorage when the session lives there (the app sends one of its values as a credential while signing in, or keeps its session nowhere else). Then Run Hound reads what the app kept there after signing in and puts it back in every new browser before the app's scripts run. An app with a cookie or localStorage session gets nothing put back, so pages that cache their reads in sessionStorage still send them, unless the session cookie is one Run Hound can't tell apart from a page script's cookie (see below).

**What sign-in can't do (yet):**

- Verification codes (multi-factor, or a code sent by email), captchas, sign-in links sent by email, "Sign in with Google/GitHub" and a password page on another site (a hosted sign-in on another domain: "The sign-in continued on another site") aren't supported; **Test sign-in** and `accounts test` say what they ran into. Turn codes and captchas off for test accounts in your development setup.
- A sign-in page that needs a Web Worker to sign in fails: Run Hound blocks workers while it types the password.
- A sign-in form that opens a new tab or window (`target="_blank"`, a popup) fails: Run Hound closes any tab a sign-in opens, since one could carry the password to another site.
- A session the app throws away when a page loads (for example a sessionStorage session tied to the tab that signed in) doesn't carry over, and the plan fails with "still shows the sign-in page".
- A sessionStorage session that sends nothing with its token while signing in, next to a cookie of the app's own site that is HttpOnly or whose name says session or token (and isn't a known load-balancer, bot-manager or firewall cookie), is taken for a cookie session: its sessionStorage isn't put back, and the plan fails with "still shows the sign-in page".
- The other way round: a cookie session whose cookie has a name that doesn't say session (no sess, sid, auth or token), isn't HttpOnly or is set by a page script when the sign-in page loads, and is kept unchanged by the submit, is taken for a sessionStorage session when the app keeps anything in sessionStorage. What the app keeps there is put back in every new browser, pages may load their data from that copy, and `access-control` can skip with "Account A has no data on this page that Run Hound can recognise" instead of reporting a real IDOR.
- Some verification-code pages called a code step only by their heading or title aren't recognised, and **Test sign-in** reports success, so the signed-in checks then run on that page: a page whose only field has no code word of its own (code, OTP, PIN, token, digit, verification …), isn't code-sized (no `maxlength` of 4 to 8, no `pattern` of 4 to 8 digits), isn't split into boxes, and either has no numeric hint (`type=number`, `inputmode=numeric`, a digits-only `pattern`; `type=tel` isn't one) or has one only under a heading that says just "verify". So is a code field whose own words say a phone number or an address with no code word ("Enter the number we sent to your phone").
- A signed-in landing page fails sign-in with "asks for a verification code" when its only field has a sign-in code word in its own label, placeholder or name (a "Phone verification" lookup), or is code-sized or says code, PIN or token under a heading with a code word, even a bare "Please verify your email address", or is numeric under a heading that names a code step ("Two-factor settings").
- An app that shows its signed-in view at the sign-in page's own address, with a field whose name or label says code or verify ("Room code"), fails sign-in with "asks for a verification code" (unchanged since 0.4.0).
- The sign-in page and the page under test must use the same host name (`localhost` and `127.0.0.1` keep their cookies apart).
- While signed in, Run Hound never clicks sign-out controls and never submits a form that sets a password (change password, sign up), even with `--allow-destructive`.
- `csrf` needs the app on `localhost` or `127.0.0.1` (its cross-site page is served on the other one); on any other host name it is inconclusive. Rate limits and file upload are planned.
- `csrf` leaves an anti-CSRF token out of the forged body only when it recognises it: by name (csrf or xsrf in it, `authenticity_token`, `_token`, `token`, `nonce`, `_wpnonce`, `form_key`, `form_token` …), or by value when the page holds it in a csrf/xsrf `<meta>`, a csrf/xsrf cookie or a hidden input. A token the app's scripts keep in memory (fetched from an API) and send in a body field under another name is replayed, so a token-protected save can then be reported as a finding.
- `csrf` doesn't forge a save whose body is a JSON array, a bare JSON value, a multipart body carrying a file or a JSON object with no text field it can forge (the page encodes the typed value): the scenario is skipped and names the body type, never a pass or a finding.
- For `csrf`, only a `400` to a forge that carried Account A's cookie, sent the save's own way with nothing left out, counts as refusing the value (inconclusive). A `409` or `422` counts as a refusal like a `403`, because Rails answers a missing CSRF token with `422`, so an app that rejects the forged value itself with `422` or `409` passes, unless a random hidden value Run Hound can't place was also left out. A plain-named random hidden value (a home-made `formToken`, Moodle's `sesskey`) refused with `403`, `419`, `401` or `415` passes, and an app with a real defence that answers `403` while a reference-looking value (`list_id`, a UUID) was left out is inconclusive. A `202 Accepted` that stores the forge only after the re-read passes.
- `write-access` replays the body of your app's own update, and of its headers only an anti-CSRF token (`X-CSRFToken`, `X-XSRF-TOKEN`, `X-CSRF-Token`) as B's own, read from the same csrf/xsrf cookie or `<meta>` on a page opened as B, or from the header's usual source (`XSRF-TOKEN`, `csrftoken`, `<meta name="csrf-token">`) when A's value has changed since, as Laravel's `XSRF-TOKEN` cookie does on every answer. A token the app's scripts keep in memory has no B value to read, so B's request goes without the header (as a signed-out one always does), and a `400`, `403`, `419` or `422` is then inconclusive, never a pass. No other header is sent: an update guarded by `If-Match` is refused for the missing header, which is inconclusive when the app answers `412` or `428` and reads as a pass when it answers another status (such as `422`).
- `write-access`: an app that answers `404` both for another account's record and for an out-of-date version its reads don't show is inconclusive, never a pass, and so is one that refuses an out-of-date version with `400`, `422` or `5xx`; when the app applies Account A's comparison write and its reads show a field it sets on every save (`updated_at`), the put-back leaves that field changed, so even a clean app ends inconclusive ("check Account A").
- `write-access` and `csrf` are skipped on a GraphQL app that reads with `POST /graphql` (no `GET` reads the saved record back, and its updates don't name the record in their address); when the form's save reached the app, the note names it and says "check Account A". The form's own mutation is held first: one that names a record the page read, or whose name doesn't say it creates a record (`updateProfile`, `saveSettings`, `submitProfile`), is stopped before it reaches the app. A persisted query (a hash with no query text) is judged by its operation name, and after the form's create has gone through, a later mutation that doesn't read as a create goes only when it names the record that create made. A REST save with a `query` field (a saved search) is never taken for a GraphQL read, unless its body is only `{"query": …}` with text that happens to be valid GraphQL shorthand (then it goes through unjudged). A persisted query sent as `{id: <hash>, variables}` with no query text, no `doc_id` or `documentId`, no `extensions.persistedQuery` and no `operationName` (Hot Chocolate's shape) is neither learned as a read nor judged as GraphQL, so on such an app a form that edits a record the page read that way can reach the app and change it: check Account A.
- `paywall-trust`: a plan change that lands more than about 5 s after the page or Billing tab that caused it (a slow job queue) is put down to a page Run Hound opened later, or, when it lands after the quiet read that follows the last page, isn't seen at all, so the scenario can pass while A is on the paid plan. When the page under test is itself a success page that grants on load, a grant before Run Hound first reads A's plan skips the scenario as "already has a paid plan", and one within about 5 s after it ends the scenario inconclusive: test the billing or settings page that links to it instead. On a slow app the 5-second waits can use up the probing time, and the run then ends inconclusive, naming the pages it didn't open. A page that loaded runs its own requests during the wait, as for a visitor who stays on it (a checkout or portal request on a timer reaches the app); only its page loads to a checkout or portal start are held. The exported spec reads the plan for at most 60 s, so a grant that took more than about 55 s to show is reported but its spec may pass.
- `paywall-trust`: a cancel or downgrade control that opens a new window is never followed (Run Hound never loads a new window's first page), so the restore counts as failed and the notes say "check Account A". A page's own navigation to a page of the app whose path doesn't name a checkout, subscription or portal start (for example `/go/manage`) is let through; a redirect from there to a payment provider is blocked, but the app's server may already have created the checkout or billing portal session.
- `page-controls` and `dead-control` (both ticked by default: the buttons outside and inside a form) click a plan button whose name doesn't look destructive ("Switch to Free", "Go back to Free", "End my subscription", "Choose Pro", "Start free trial") on any run, signed in too, and with destructive scenarios allowed also "Cancel subscription", "Cancel plan" or "Downgrade": sign in with a test account whose plan you can reset.
- Signed in, on a page with a form that shows the account's own email (a profile form), `axe-states` and `pii-leak` save a test address over it, and nothing puts it back: untick them there, or use a test account whose email you can change back. `deep-links` opens the app's own success pages like any other link, so an app that grants a plan when one loads moves A to it.
- Signed-out replays send no credential header, not even a Supabase client's public `apikey` (the anon key), so against a local Supabase the signed-out scenario of `access-control` is refused by its API gateway before row-level security is asked.
